## Model / workload

- Script: `examples/batch_10k_skus.py`
- Model: per-SKU `y = intercept + trend*t + seasonality*sin(t) + Normal(0, sigma_i)`,
  3 estimated parameters per SKU, N_SKUS=100 independent SKUs, 44 weeks train data each.
- **Corrected claim**: this script's docstring and the README/docs previously said
  "10,000 SKUs"; the actual N_SKUS in this script is 100 and always has been — there is
  no benchmark run in this repo backing a 10,000-SKU number.
- True/simulated values: per-SKU `true_noise[i] ~ Uniform(3, 15)`.
- Estimated vs. fixed: intercept/trend/seasonality are estimated on every engine;
  `sigma = true_noise[i]` (the true simulated per-SKU noise) is fixed/known on every
  engine — same parameter count (3 per SKU) everywhere.
- Chains: 4 (all engines — **corrected**: rustmc's `batch_sample` previously defaulted
  to `chains=1` while the PyMC+nutpie loop used `chains=4` explicitly, a 4x work
  imbalance that was never called out). Warmup: 500 (all engines). Draws: 1000 (all
  engines).
- Seed: 42, explicit on every engine.
- Threads/processes: rustmc runs all 100 x 4 = 400 chains through a single shared Rayon
  thread pool (24 logical CPUs). PyMC+nutpie runs each SKU as a separate
  `nutpie.compile_pymc_model` + `nutpie.sample(..., cores=4)` call in a Python loop — i.e.
  100 sequential per-model compiles, each spawning 4 worker processes.

| Phase | rustmc (100 models, 400 chains total) | PyMC+nutpie (100 sequential compiles, 4 chains each) |
|---|---|---|
| Model construction | 0.001s | included in per-model loop below |
| Compilation | shared/lazy, see note | ~significant — compiled once per SKU, not amortized |
| Sampling | 0.575s (compile+sample combined) | 388.87s (compile+sample combined, summed over 100 models) |
| Post-processing (ESS/R-hat over 300 param traces) | 0.663s | included above |

## Result

- Raw output log: see `benchmarks/results/batch_10k_skus.py.log` (generated by
  `python examples/run_benchmarks.py`).
- Honest conclusion: rustmc is dramatically faster here (roughly 300x wall time, ~185x
  ESS/s) because it amortizes one Rayon thread pool across all 400 chains with no
  per-model compilation, while nutpie pays a full model compile for each of the 100
  SKUs sequentially. That per-model compile cost is real and would shrink relative to
  rustmc's advantage as `N_SKUS` grows, which is the core selling point of the batch API.
  However, rustmc's max R-hat (1.0657) exceeds the conventional 1.01 convergence
  threshold and it produced 1317 divergences where nutpie produced 0 on the identical
  per-SKU model/data/seed — the speed advantage comes with a real, measurable
  convergence-quality cost on this workload that should not be hidden behind the
  headline speedup number.
- The forecast MAE for both engines is nearly identical (5.52 vs. 5.56), so despite the
  R-hat/divergence gap, the posterior means themselves were similar for this particular
  SKU — this does not generalize to "convergence doesn't matter here" without checking
  more SKUs.

## Reproduction

```bash
python examples/batch_10k_skus.py
# or:
python examples/run_benchmarks.py --only batch_10k_skus.py
```

Runtime note: the PyMC+nutpie side takes ~6.5 minutes on the reference hardware above
because of 100 sequential per-model compiles; this is the slow part of the whole suite.
